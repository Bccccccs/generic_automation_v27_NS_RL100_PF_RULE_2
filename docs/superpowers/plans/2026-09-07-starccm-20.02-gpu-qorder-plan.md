# STAR-CCM+ 20.02：CCM 模块 GPU 并行计算改造实施计划

> **交接对象：qorder。** 逐项执行本计划中的复选框；若执行器支持 skills，使用 `superpowers:executing-plans` 按任务推进。每个任务先验证现状、补充失败测试、实施、验证和审查，再进入下一任务。本文件是计划，不代表功能已经实现或真实 GPU 算例已经验收。

**Goal：** 为现有 `scripts/workflow.py ccm` 增加显式启用的 Linux STAR-CCM+ 20.02 GPU 原生求解能力，限定单个计算节点内使用多张 GPU，单卡仅作为可选验证基准；现有 CPU 支持和其他功能保持不变。

**Architecture：** 默认 CPU 路径保留原样；仅在 `compute_backend=gpu` 时进入新增的 GPU 配置、资源预检和执行证据分支。GPU 相关实现放在 `starccm/runtime/` 的独立文件，通过现有 CCM CLI 和 runner 接入，输出单独的 GPU 证据文件；不修改喷气控制宏、数据采样和下游算法。

**Tech Stack：** 现有 Python、argparse、dataclasses、subprocess、pytest；STAR-CCM+ 20.02 系列 / 2502；Linux、现有 MPI / SSH / Slurm。GPU 由 STAR 自身求解器使用，不增加 PyTorch、CuPy、Numba 或自研 CUDA 求解器。

**Spec：** 本文件第 1、4、5、6 节是实施约束及接口规格，与后续任务一起交付。

**编制日期：** 2026-09-07。用户最终明确：仅申请一个 Linux 计算节点，在该节点内调用多张 GPU；本计划不设计跨节点 GPU 流程或多节点状态。显卡厂商、型号、数量、驱动、完整 STAR build、许可证、真实 `.sim` 模型清单尚未给出。不得自动假定为 NVIDIA、A100、固定显存或固定 MPI。

## 1. 全局约束：任何任务均不得突破

1. **默认仍是 CPU。** 未传新增参数的旧命令，构建出的 STAR argv、并行资源解析、MPI 环境、运行模式、产物契约和异常行为均应保持。
2. CPU 不检查 GPU、不探测驱动、不调用 `nvidia-smi`、不要求 20.02、不增加 GPU 依赖、不注入 `-gpgpu`、不自动升级 STAR。旧 17.06 CPU 配置继续可用。
3. CPU 的 `--np` / `num_cores` 仍表示 STAR 进程数，不能改成显卡数、线程数或乘以 GPU 数。
4. GPU 必须显式选择；不设“检测到显卡就启用”的自动模式。不提供自动回退 CPU 的重跑功能。
5. 不改变真实 `.sim` 的物理模型、网格、精度、初场、边界、时间步、迭代终止条件、report 定义和采样周期。GPU 不兼容则报告阻塞，不能通过关闭物理模型来通过。
6. 不修改 `build_flow_control_macro()` 的求解循环、report 读取、Java 源码模板和 24 路边界设置。旧 CPU 宏和 GPU 宏在相同输入/相同输出路径下必须逐字节一致。
7. `J01..J24` 喷口与 `JET01..JET24` 底面区域不能混淆；质量流量命令、STAR 原始实际质量流量、符号转换后的实际质量流量保持现有关系。
8. 不改变 `sample_ownership`、物理时间对齐、六区力、总力和力矩、`Jet_Reaction_Z` 语义，不修改 B04/B52/B53/B54、ROM、RL、Mock、训练数据生成和图表算法。
9. 许可证信息只在现有执行路径内使用；新增 GPU 文件、诊断和可提交 fixture 必须脱敏，不保存 PoD 密钥或完整环境变量。不得顺带重构历史日志体系。
10. 未取得真实运行证据时写 `UNVERIFIED` / `BLOCKED`，不能把 dry-run、Mock、Python 测试通过或 STAR 退出码 0 宣称为 GPU 求解验收通过。
11. 逐个功能提交，提交标题和正文必须中文。仅提交实施者本次修改，禁止 `git add .` 把其他工作一起带入。推送需要执行任务的授权，本计划交付不自动提交或推送。
12. GPU 拓扑固定为一个节点；不增加跨节点调度、逐主机 GPU 文件、远端设备发现或多节点状态机。旧 CPU 多节点能力按原代码保留。
13. 任何超出白名单的修改、CPU 数值变化或物理设置变化必须先作为独立变更报告，不得隐含进 GPU 优化。

### 2.3 用户补充的 CHPC 参考：已核对并纳入

[CHPC STAR-CCM+ 运维指南](https://wiki.chpc.ac.za/howto:starccm) 是该中心的原始运行说明。它列出 20.02.007 容器，但 GPU 示例使用 17.06；采用 PBS，并规定该 GPU 用法一张卡对应一个 MPI rank。页面称其 GPU 作业不支持跨节点，且资源并未普遍开放；这些是站点边界，不是 STAR 的普遍限制。单卡及三卡脚本使用 `$nproc`，展示片段未定义它；容器流程的 Intel MPI 限制也仅针对该部署。[CHPC 指南](https://wiki.chpc.ac.za/howto:starccm)

据此对本项目作以下工程修订：

1. **首批批准配置固定为每 GPU 一个 MPI rank。** 单卡 np=1、两卡 np=2。其他比例留作取得同版本/目标站点依据后的性能试验，不作为初始默认，也不继承 CPU 满核配置。
2. 分清 `ncpus`（分配的 CPU 资源）、`mpiprocs`/STAR `--np`（进程数）和 `ngpus`（GPU 数），不能从分配 CPU 总数推断 GPU rank。例子中的进程变量要显式定义并与分配校验。
3. 本项目已有 Slurm/manual，故不新增 PBS scheduler。目标站点若用 PBS，可先以经过站点审核的外部作业脚本分配资源，再接 manual + machinefile，并提供 GPU 分配证据；没有适配证据就 BLOCKED。
4. 按用户最终范围，只实现单节点多卡。CHPC 的站点限制仅作为背景，不引入跨节点适配任务。
5. 不复制远端指南中的许可证地址、PoD 样例、用户目录、容器名、精度建议和性能倍数。许可证按本项目已有配置，精度保持冻结值，速度由本项目实际测量。
6. 将 **原生安装 / 容器启动** 纳入 G0。`--starccm-path` 接收单个可执行文件路径，不能塞入包含空格的一整条容器命令。若目标部署仅提供容器，需要站点已核验的可执行 launcher wrapper；要求正确透传每个 argv、返回码、本节点 GPU 可见性、MPI、输入/输出路径及 `-version/-help`。wrapper 位于 GPU 专用部署目录并记录 hash，不修改 CPU PATH、用户 `.bashrc` 或旧启动命令。
7. 多卡预检登记 GPU 互联拓扑，分别测通信与求解耗时；不把 NVLink 当所有机器的强制条件，也不把 PCIe 平台未测试说成已加速。

这份参考增强了集群实施方案，但没有解除 20.02 完整手册、目标物理模型与真实 GPU 日志的核验关卡。

### 2.5 候选命令及其核验限制

候选最小差异：在原命令 `-batch` 之前加入 `-gpgpu <selection>` 和 `-require-gpgpu-compatibility`。`-np` 继续独立指定 STAR 进程数量。旧版 Siemens 命令参考还列出 `auto:N`、显式设备列表和 `:nomps`；严格兼容选项用于阻止不兼容 solver 在执行时退回 CPU。[S6 命令参考](https://www.tech-doc.cn/wp-content/uploads/Free/StarCCM2406/GUID-A871C88B-038B-48AE-80F4-886521497B0F.html)

单节点资源关系按下表落实，CPU 分配与 MPI 进程数分别记录：

| 当前节点 GPU 数 N | 初始 STAR MPI ranks | CPU 资源 | 用途 |
|---|---|---|---|
| 1 | 1 | 至少满足该 rank 和 launcher 所需资源 | 算例可装下时的参考 |
| 2 | 2 | 由站点核验后申请，不等同 GPU 数 | 首个多卡验收配置 |
| 4 或实际分配的 N | N | 由站点核验后申请，不使用 CPU 满核数代替 ranks | 同节点扩展测试 |

GPU 预检从实际选择器/设备列表得到 N，首批资格要求 `num_processes == N` 且本次分配含 N 张可见卡。申请了 N 张卡却实际只激活部分卡，必须判本配置未通过。Slurm 提交示例固定 `--nodes=1`；task 数、GPU 数及队列语法按目标站点生成。当前 runner 仍只消费已经存在的分配，不承担资源申请。

本项目设计选择：默认 GPU 请求使用带数量的选择器，NVIDIA 初始测试关闭 MPS，禁止 `force:` 和不受约束的 `auto`，最终以目标 20.02 的 help/手册确认的语法生成。渲染 GPU 参数如 `-rgpu` 不作为求解加速入口。显卡编号要核验 STAR、CUDA 可见设备与实际 UUID 的映射，不能直接照抄宿主机编号。

**此处规则是项目的保守策略，不是对所有 STAR 版本的限制声明。** 文档未核实的驱动下限、显存比例、GPU 卡型和许可证数量不填写猜测值。

## 4. 设计选择与修改白名单

### 4.1 方案比较

| 方案 | 收益 | 代价与结论 |
|---|---|---|
| 仅提供裸 `--extra-args` | 快速试验 | 无严格模式、资源约束与证据；不作为交付方案 |
| 独立 GPU 执行配置 + 现有 CPU 路径保持 + GPU 证据文件 | 修改边界小，可回归、可审查、可验证实际运行 | **推荐并采用** |
| 重构全项目启动器、统一两个 adapter、自动调参/采样降频 | 理论上统一程度高 | 会影响 CPU 和其他业务，违反本次范围，排除 |

### 4.2 允许修改的现有文件

## 5. 接口规格

### 5.1 CLI

| 新参数 | 默认 | 约束 |
|---|---|---|
| `--compute-backend {cpu,gpu}` | `cpu` | 不接受 `auto` |
| `--gpgpu SELECTION` | 无 | GPU 必填；CPU 携带此参数报明确参数错误 |
| `--gpu-qualification PATH` | 无 | GPU 的 `run` 必填；dry-run 可不提供；不自动从项目 YAML 查找 |

已有 `--np`、`--scheduler`、`--slurm-job-id`、`--machinefile`、`--mpi-env` 语义保持。GPU 必须显式 `--np >= 1`；CPU 仍沿用原有推断。不新增 `--allow-cpu-fallback`，严格兼容参数自动附加且不可关闭。

GPU 选择器拟支持的子集，以任务 0 的同版本核验为实现前提：

- 单节点：`auto:1:nomps`、`auto:2:nomps` 等；或 `0:nomps`、`0,1:nomps` 等显式列表。
- 不带 `:nomps` 的形式只在资格文件证明站点允许对应 MPS 行为，或目标厂商不适用此后缀时开放；不能默默删后缀重试。
- 不实现 `file:` 选择器；本次只在同一节点用数量或显式卡列表选择 GPU。
- 拒绝 `force:`、裸 `auto`、重复/负数设备、`auto:0`、shell 片段、换行、多个选择机制混用。
- qualification、可执行程序和 sim 路径允许正常空格，作为独立 argv 元素传递，不用 `shell=True`。
- CLI 在获分配的计算节点上运行；记录并核对当前 hostname 与分配的唯一节点，短名/FQDN 规范化处理。无需新增远端节点探测。

### 5.2 Python 类型：新增配置放在 dataclass 尾部

```python
# starccm/runtime/gpu_config.py

from typing import Literal

@dataclass(frozen=True)

    backend: Literal["cpu", "gpu"] = "cpu"
    selection: str | None = None
    qualification_path: Path | None = None

class GPUConfigurationError(ValueError):
    pass

    """纯函数：校验配置，CPU 返回空 tuple，GPU 返回同版本已核验 token。"""
```

在 `FlowControlStarCCMRunConfig` 最后新增：

```python
gpu: GPUExecutionConfig = field(default_factory=GPUExecutionConfig)
```

不要把新字段插入旧字段中间，避免破坏位置参数构造。`FlowControlStarCCMRunResult` 不必改变，sidecar 路径由 `output_dir / 'gpu_execution.json'` 明确约定。

`_build_starccm_command()` 增加末尾 keyword-only 参数：

```python
gpu: GPUExecutionConfig | None = None
```

保留原函数中所有现有 argv 拼装代码；只在原 `command += ['-batch', ...]` 之前插入：

```python
if gpu is not None and gpu.backend == "gpu":
    command.extend(gpu_command_tokens(gpu))
```

配置一致性由 runner 入口和 `gpu_command_tokens()` 校验，CPU 带 selection 等矛盾配置不得被这里直接忽略。构建器增加可选参数后的 CPU 返回值必须与旧函数精确相等。`num_cores=1` 时 CPU 不添加 `-np` 的现状同样保留；GPU 单 rank 是否显式发出 `-np 1` 由同版本启动要求核验，若需要，只加在 GPU 分支。

### 5.3 预检模块接口

```python
# starccm/runtime/gpu_preflight.py

from typing import Any

@dataclass(frozen=True)

```

所有外部诊断使用参数列表，设置单命令超时（初始 15 秒，可用模块常量），捕获返回码/stdout/stderr；超时不是“设备不存在”的同义词，分类记录。新增诊断仅在当前节点运行，不拼用户原始 shell 片段。

### 5.4 资格文件：人工核验信息与实时证据分离

`--gpu-qualification` 指向 JSON，类型是 `ccm_gpu_qualification_v1`。读取函数：

```python
# starccm/runtime/gpu_qualification.py
from pathlib import Path
from typing import Any

def load_gpu_qualification(path: Path) -> dict[str, Any]:
    """拒绝缺字段、错误类型、不支持 schema、失效证据；不启动任何命令。"""
```

必须字段：

- `schema_version`、`reviewed_at`、`reviewer`。
- `star_release`、完整 `star_build`、`precision`；不能只有目录名字或 `20.02`。
- `documentation`：每项含 title、build、chapter、source（官方 URL 或安装文档路径）、sha256（可取得离线文件时）；在线文档不得编造 hash。
- `approved_platforms`：明确 OS/CPU 架构/GPU vendor/model、匹配规则、驱动要求、对应依据；不使用无限通配。
- `approved_launch`：native/container/wrapper 及其身份/hash、scheduler、MPI 实现/版本、启动方式、rank 与 GPU 数的批准范围、MPS 策略、固定单节点和可用 GPU 数量及来源。
- `sim_review`：真实输入 sim 的 SHA256、模型/solver/interface/运动/report 清单、每项的 compatible/incompatible/unknown 和来源；unknown/incompatible 阻止正式 GPU run。
- `required_flags`：本 build 实际支持的 GPU 和严格兼容参数。

该文件代表“具备试跑条件”，**不代表 GPU 已成功执行**。首次 smoke run 使用已审核的真实模板与文档资格即可启动，不要求先有成功日志，从而避免循环依赖。对最终 GPU 结果的确认仍必须由实际日志和验收完成。

每次 run 比对实时版本、平台、节点分配和输入 hash；旧资格不能为换卡、换 build、换 `.sim` 自动背书。不要自动创建内容全为支持的样例文件。示例使用测试 fake 信息时，明确 `test_only=true` 并强制生产拒绝。

### 5.5 GPU 证据 sidecar

不改 `timeseries.csv`、runtime plan 或 B04/B53/B54 schema。每次 GPU 请求在 `raw_star/gpu_execution.json` 记录：

```json
{
  "schema_version": "ccm_gpu_execution_v1",
  "request": {
    "backend": "gpu",
    "selection": "auto:1:nomps",
    "mpi_processes": 1,
    "strict_compatibility": true
  },
  "state": "UNVERIFIED",
  "actual_backend": "unknown",
  "star_return_code": null,
  "failure_code": null,
  "evidence": [],
  "node": null,
  "devices": [],
  "inputs": {},
  "timing": {},
  "outputs": {},
  "qualification_sha256": null
}
```

以上仅为结构示例，不是真实运行记录。生产记录补充当前节点 hostname，以及本次所用 GPU UUID/PCI 地址/可见序号、设备名称、显存、驱动、版本、MPI 映射、分配来源、sim/schedule hash、日志 hash 和时间戳。未知字段写 null；不可用请求值填充 `actual_*`。

公开接口：

```python
# starccm/runtime/gpu_evidence.py
from pathlib import Path
from typing import Any

class GPUExecutionError(RuntimeError):
    pass

def parse_gpu_log(text: str, *, star_build: str) -> dict[str, Any]:
    """按已验证 build 的日志模式返回设备、solver、回退和错误证据。"""

def write_gpu_evidence(path: Path, data: dict[str, Any]) -> None:
    """临时文件 + 原子替换；单一 runner 写入者。"""

def validate_gpu_completion(
    evidence: dict[str, Any], *, expected_node: str
) -> None:
    """缺失 GPU 实际执行或发现回退/分配不符时抛 GPUExecutionError。"""
```

GPU 状态序列：`UNVERIFIED → PREFLIGHT_PASSED → RUNNING → GPU_CONFIRMED`。失败为 `BLOCKED`（未启动）或 `FAILED`（已启动）。`GPU_CONFIRMED` 只确认 GPU 执行及完整运行证据；物理等价性和性能另在验收报告判断，不能将三个结论混为一体。

`actual_backend` 允许 `unknown/gpu/cpu/mixed`。`gpu` 表示纳入资格审查的求解路径使用 GPU，并不宣称 Python、Java、IO 或每个控制操作都在显卡上。需要区分正常 CPU 辅助开销和不兼容 solver 的 CPU 回退。

运行结束时至少同时满足：STAR 正常退出；读取的是本次新日志；存在目标 build 的明确 GPU solver 执行证据；节点/设备/rank 与分配吻合；未发现不兼容/CPU 回退；完成预期时段及现有必要产物。否则 GPU 结果不能判通过，即使退出码为 0。

日志正则必须来源于**实际 20.02 脱敏日志**，先采集再编写；不在计划中虚构 Siemens 日志句式。不熟悉的 build/句式按未知处理，不用搜索字符串 `GPU` 或只看 `nvidia-smi` 利用率认定成功。Mock fixture 只能验证状态机，不能认证真实解析器。

## 6. CPU 不变与运行模式矩阵

| 场景 | 必须保留 / 新增的行为 |
|---|---|
| 默认 CPU、显式 CPU、旧 Python 调用 | 旧 argv/宏/产物/错误行为一致；零 GPU 外部命令；不产生 sidecar |
| CPU manual 单进程/多进程/machinefile | 原 `-np` 省略规则、`-rsh ssh`、machinefile slot 验证一致 |
| CPU Slurm | 原资源推断、SSH 预检、默认 UCX 变量一致 |
| CPU Windows `.bat/.cmd` | 原 `cmd /c` 引用与流式日志保持 |
| GPU dry-run | 仅解析配置、生成原宏/plan 和 `UNVERIFIED` sidecar；不运行 GPU/STAR 探测；不把请求设备写成实际设备 |
| GPU run | 资格 + 实时资源预检通过后启动；失败不得 CPU 重跑 |
| GPU package-only / validate-only | 使用既有产物；不检测 GPU/不启动 STAR；不覆盖已有实际 GPU 证据，不凭参数生成成功状态 |
| 所有模式涉及 Slurm | 旧 CLI 原本会先解析 Slurm 分配，不能在本功能中默默改变 CPU 行为；离线生成优先 manual 模式；GPU dry-run 的“不探测”指新增 GPU/STAR 探测 |

GPU `run` 的目录/lock 检查必须在现有宏和 runtime plan 写入之前完成，避免检查时已经覆盖旧产物。GPU `run` 使用全新独立输出目录，若已有 `timeseries.csv`、STAR 日志、结果 sim 或 GPU sidecar，返回 `OUTPUT_REUSE_FORBIDDEN`，避免中断/旧产物冒充新结果。此拒绝只作用于 GPU run；dry-run 后转 run 可允许目录只含生成的宏、plan、复制的 schedule 和 `UNVERIFIED` sidecar，逐项验证后覆盖该离线请求记录。

同一 GPU run 目录只允许一个 writer。启动前以独占创建方式获取 GPU 专用 lock，记录本进程信息；正常完成及异常退出释放。本次进程不自动移除未知残留 lock，不杀其他 STAR/MPS 进程。`ccm-status` 只读 GPU sidecar，不回写 GPU 状态，防止覆盖 runner；其原 CPU manifest 更新继续保持。

## 8. 验收矩阵和性能判定

### 8.1 四层关卡

| 关卡 | 验证内容 | 必须产物 |
|---|---|---|
| A：CPU 不变 | 改造前后同环境 argv、默认行为、宏、失败路径、旧 CPU 能力 | 特征测试、完整测试结果、原宏 hash 比较 |
| B：GPU 真执行 | 本节点各张 GPU 的 solver 证据、设备分配、严格兼容、不回退 | 原始脱敏日志、GPU sidecar、资格与分配证据 |
| C：物理结果 | 同 build/精度/初场/模型/调度的 CPU/GPU 对比，现有质量门 | 原始/处理后时序、字段映射、差异报告、B04/现有质量结果 |
| D：性能收益 | 正确性通过后比较求解时间和全流程时间 | 重复实验表、性能/显存/资源利用率记录 |

A 不通过就拒绝改动。B 通过但 C 失败不能发布为可用求解后端。C 通过但 D 无提升，应诚实报告“GPU 功能成立，当前算例未证明加速”，不要为了出现加速数字改其他功能。

### 8.2 CPU/GPU 结果如何比较

- 严格保持 schedule 字节/hash、24 路命令、time step、窗口边界、采样数量/时刻、report 清单；不会为对齐而丢行、平移时间或插值修饰结果。
- 数值使用显式物理时间及现有 ownership 对齐；同一运行方式应相同的窗口/样本归属精确一致。不能仅凭行数相等 zip 两个表。
- 比较所有 `star_actual_massflow_01..24`、`actual_massflow_01..24`，六区载荷、Fz_Total、Drag_Total、Pitch_Moment、Roll_Moment 和现有必需报告；保持各自单位/符号。
- 对每列报告绝对最大误差、均方根误差、峰值/均值差、积分差；`Jet_Reaction_Z` 只能按已有定义比较，不能把语义未确认变成确认。
- GPU 并行归约顺序可能导致浮点差异，因此不要求物理结果逐 bit 相等；CPU **软件兼容**要求与 GPU **数值等价**要求要分开。
- 通过阈值必须在看到 GPU 结果前冻结；针对实际物理尺度、离散误差及两次 CPU 重复差异确定。每列都要在验收配置写入有单位的 `atol` 和无量纲 `rtol`，以 `abs(gpu-cpu) <= atol + rtol*abs(cpu)` 判定适用的瞬态逐点比较。
- 物理容差尚未定义时，执行器输出完整差异统计，并将 C 标记 BLOCKED，不自行宣称 1%/5% 都可接受。接近零的质量流量使用有物理依据的绝对容差，不以极小分母制造假相对误差。
- 若实际使用 LES/DES 等使长期逐点轨迹不适合作为唯一判据，应在实验前定义统计稳定区间、均值/RMS/频谱及置信区间；这需要明确的物理审核，不得事后换指标掩盖失败。
- 现有 schema、质量、物理/provenance 门照常执行；GPU 成功不能消除原本存在的 B54 数据/物理证据缺口。

### 8.3 试验表

| 组别 | build / 输入 | 资源 | 目的 |
|---|---|---|---|
| C-old-before / C-old-after | 原支持 CPU build，原样输入 | 原 CPU 配置 | 证明原 CPU 能力未破坏 |
| C20 | 同一个 20.02 build、同精度、冻结 sim/schedule | 固定 CPU 核心数 | GPU 数值与性能参考 |
| G1 | 同上 | 1 GPU + 已批准 ranks | 单卡可运行、正确性、显存 |
| G2 | 同上 | 单节点 2 GPU + 已批准 ranks | 多卡并行和通信开销 |
| GN | 同上 | 同一节点实际分配的更多 GPU | 只在分配/显存条件具备时测试 |

`speedup = median(T_cpu) / median(T_gpu)`；同规模 GPU 扩展效率另用 `T_G1 / (k * T_Gk)`。如果单卡装不下，不能伪造 G1，改为最小可运行 GPU 组作为扩展参考，并注明公式基准变化。

推荐优化流程：先确定能装下且正确的最小 GPU 数，再比较更多卡；rank/GPU 从通过手册审核的保守配置开始，再单变量调整。不存在所有模型通用的“核数越多越快”。不承诺官方其他案例的倍数能复制到本项目。

| 版本/精度/Java 宏不兼容 | 保存 build、失败日志，单列兼容阻塞 | 改 CPU 默认版本或全局宏 |
| 模型不支持 GPU | 说明具体 solver/model，保留 CPU 现有功能 | 删除模型、换模型、悄悄回退 |
| GPU OOM | 记录每卡显存和网格，评估更大显存/更多已分配 GPU | 改粗网格、降低精度、放宽收敛 |
| Slurm GPU 不可见/未分配 | 明确资源阻塞，由正确作业上下文重试 | 占用节点其他用户 GPU |
| MPI / UCX 失败 | 对 GPU 路径单独诊断并记录站点适配 | 修改 CPU 原有 UCX 修复值 |
| 许可证失败 | 保存脱敏错误，由现有许可管理处理 | 自动切授权方式或泄漏 key |
| 日志未知 | 未确认；补真实 fixture 后再开放 build | 只依据 returncode=0 判通过 |
| 性能比 CPU 慢 | 报告 IO/通信/求解段占比和结果 | 降低采样频率或少导出字段 |
| 被中断/输出已存在 | 保留失败记录，新目录重跑 | 拼接旧/新 CSV、覆盖原始证据 |

恢复到 CPU：显式使用原 CPU 命令或 `--compute-backend cpu`，删除本次命令中的 GPU 专用参数，使用原始冻结输入和新的输出目录。不能拿更高版本保存的 GPU 结果 sim 直接作为旧 CPU build 的输入；原模板始终保留。

## 10. 操作示例：实现完成且 G0 通过后才能用于真机

以下是命令结构，环境变量由操作人员设置为实际路径/已分配资源。示例不预设显卡型号、许可证或站点分区。不要直接将未展开变量记录为真实 provenance。

### 10.1 CPU：原命令保持

```bash
PYTHONPATH=. .venv/bin/python scripts/workflow.py ccm \
  --schedule "$CCM_SCHEDULE" --sim "$CCM_SIM" --out "$CCM_CPU_OUT" \
  --starccm-path "$CCM_BIN" --region "$CCM_REGION" \
  --np "$CCM_CPU_RANKS" --execution-mode run
```

不加新参数仍是 CPU；原 `--time-step`、`--machinefile`、`--mpi-env`、`--scheduler`、许可证使用方式均继续按原场景传入。

### 10.2 离线生成 GPU 启动方案

```bash
PYTHONPATH=. .venv/bin/python scripts/workflow.py ccm \
  --schedule "$CCM_SCHEDULE" --sim "$CCM_SIM" --out "$CCM_GPU_DRY_OUT" \
  --starccm-path "$CCM_BIN" --region "$CCM_REGION" \
  --np 2 --compute-backend gpu --gpgpu auto:2:nomps \
  --execution-mode dry-run
```

输出仍为原宏和 runtime plan，另有请求 sidecar，状态 UNVERIFIED。这个示例不能说明机器已经有两张可用卡。

### 10.3 Linux 单机两卡

```bash
PYTHONPATH=. .venv/bin/python scripts/workflow.py ccm \
  --schedule "$CCM_SCHEDULE" --sim "$CCM_SIM" --out "$CCM_GPU_OUT" \
  --starccm-path "$CCM_BIN" --region "$CCM_REGION" \
  --np 2 --compute-backend gpu --gpgpu auto:2:nomps \
  --gpu-qualification "$CCM_GPU_QUALIFICATION" --execution-mode run
```

`2 ranks / 2 GPUs` 是需要在 G0 审核的初始测试配置，不是普遍最优建议。NVIDIA MPS 后缀对本机 build 不适用时，以已核验资格生成对应示例，不能照抄。

### 10.4 已分配的单节点 Slurm GPU 作业内

```bash
PYTHONPATH=. .venv/bin/python scripts/workflow.py ccm \
  --schedule "$CCM_SCHEDULE" --sim "$CCM_SIM" --out "$CCM_GPU_OUT" \
  --starccm-path "$CCM_BIN" --region "$CCM_REGION" \
  --scheduler slurm --slurm-job-id "$SLURM_JOB_ID" --np "$CCM_GPU_RANKS" \
  --compute-backend gpu --gpgpu "auto:${CCM_GPU_COUNT}:nomps" \
  --gpu-qualification "$CCM_GPU_QUALIFICATION" --execution-mode run
```

此命令使用已存在的 Slurm 分配，不申请 GPU。`examples/ccm_gpu/` 中 sbatch 示例只能在取得站点 partition/account/GRES 规则后编写；不能把 GPU 专区名、设备数量或 QOS 编造为真实值。启动路径未通过本节点 GPU 分配隔离验证时，不执行本示例。`CCM_GPU_RANKS` 在首批配置中必须等于 `CCM_GPU_COUNT`，两者是当前节点的进程数与显卡数。

### 10.5 查看状态

```bash
PYTHONPATH=. .venv/bin/python scripts/workflow.py ccm-status --out "$CCM_GPU_OUT"
```

保留原 MPI/Step 显示，额外显示 GPU requested、actual、state 和失败原因。requested=2、actual=unknown 必须如实显示，不能打印 actual=2。
