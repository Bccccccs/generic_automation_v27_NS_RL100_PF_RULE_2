## 4.1 从站点作业脚本读到的信息（2026-09-17，未在节点实测）

来源：站点 sbatch 脚本 `run_python.slurm`（工程师 2026-09-17 指定
`--ntasks-per-node=16`、`--cpus-per-task=1`）。**这些是脚本内容，不是节点取证结果**，
不能替代 B-01/B-03 的实测。

- 加速器类型：`--gres=dcu:8` —— **海光 DCU，不是 NVIDIA**。当前 GPU 预检只实现了
  `nvidia-smi` 查询，在该节点会返回 `not_found` → `GPU_TOOL_FAILED`/`VENDOR_BLOCKED`。
  DCU 的只读设备查询命令（hy-smi / rocm-smi 之类）必须先由其自身 `--help` 确认，
  再单独实现 vendor 分支；不得用 NVIDIA 的 mock 结果认证 DCU。
- STAR build：路径含 `20.02.007-glibc2.28_double`，可执行文件为
  `.../20.02.007-R8/STAR-CCM+20.02.007-R8/star/bin/starccm+` → build `20.02.007`、
  双精度。这回答了 B-01 的 build 部分，但 `-gpgpu` 语法、`:nomps` 适用性和 DCU
  支持仍未核验。
- 分区：`hx1hdnormal01`；每节点 16 task × 1 CPU；主机内存按节点申请 `--mem=128G`（独立于 DCU 显存，先以 128G 验证，是否增大依据实际峰值与 OOM 记录）。
- 站点脚本当前**刻意只跑 CPU**，注释写明"申请 DCU 不会自动启用 STAR GPU"。这与
  本项目的 BLOCKED 状态一致：在 DCU vendor 分支与资格文件落地前，不要给该作业加
  `--compute-backend gpu`。

### 4.2 B-03 部分解除：DCU 设备与查询工具已实测（2026-09-17，节点 a14r2n09）

用户在该节点实际执行并回传输出，以下为实测结论：

- 查询工具：`/opt/hyhal/bin/hy-smi`（Hygon "C-3000 HCU system management interface"）。
  **没有 `rocm-smi`，也没有 `nvidia-smi`。** 现有 GPU 预检的 NVIDIA 分支在该节点必然
  `not_found`，必须新增 `hy-smi` vendor 分支。
- 设备数：8 张 HCU（编号 0–7），`Mode` 均为 `Normal`（未见 MIG 启用）。
- 输出格式是**固定宽度表格**，没有 nvidia-smi 那种 `--format=csv`。解析器不能照抄
  NVIDIA 的 CSV 逻辑；稳妥做法是逐卡调用
  `hy-smi -d N --showuniqueid --showproductname --showbus --showdriverversion ...`
  逐字段取值。
- 已确认存在的字段入口：`--showuniqueid`（UUID 等价物）、`--showproductname`、
  `--showbus`、`--showdriverversion`、`--showmemvendor`、`--showmemuse`（已用显存）、
  `-u/--showuse`、`--showhcuutil`、`--mig`（MIG 显示）。
- **尚未确认**：显存总量的字段、计算进程/占用查询（DEVICE_IN_USE 检查依赖它）、
  以及是否存在机器可读输出。`--help` 只回传了前 60 行。

因此 B-03 从 BLOCKED 变为**部分解除**：厂商/工具/设备数已实测，字段全集与占用查询
待补。在补齐之前不写 DCU 分支代码。
