### 4.3 B-03 全部解除 + 首次真机 `-gpgpu` run（2026-09-18，节点 f11r2n19 / f11r2n13）

在 4.2 的基础上补齐了字段全集和占用查询的真机证据，随后实现了 `hy-smi` vendor
分支（`starccm/runtime/gpu_preflight.py`，测试见
`tests/test_starccm_gpu_preflight_hygon.py`）。

**补齐的字段（`--json` 输出，真机实测）**：

- `hy-smi --showuniqueid --json` → `{"card0": {"Unique ID": "..."}, ...}`
- `hy-smi --showbus --json` → `{"card0": {"PCI Bus": "0000:09:00.0 --> SN: ... --> OAM ID: N"}, ...}`
- `hy-smi --showproductname --json` → `{"card0": {"Card Series": "BW", "Card Vendor": "C-3000 IC Design Co., Ltd."}, ...}`
- `hy-smi --showmeminfo vram --json` → `{"card0": {"vram Total Memory (MiB)": "65520", ...}, ...}`
- `hy-smi --showdriverversion`（**不支持 `--json`**，纯文本）→ `Driver Version: 6.3.31-V1.5.0a`（全卡共用，非逐卡字段）
- `hy-smi --mig`（**不支持 `--json`**）→ 与默认 `hy-smi` 同构的汇总表格，`Mode` 列 `Normal`=未启用 MIG
- `hy-smi --showpids`（**不支持 `--json`**，占用查询）→ 逐 PID 文本块，含 `HCU Index`/`PCI BUS`/`VRAM USED(MiB)`，**没有进程名字段**（用本机 `/proc/<pid>/comm` 补，只读）

**驱动版本格式问题**：实测串 `6.3.31-V1.5.0a` 带构建后缀，原有的纯数字点分驱动比较
逻辑会对任何海光驱动串判"无法解析"。已改为只取数值点分前缀比较（对 NVIDIA 的纯数字
驱动串行为不变）。

**Slurm Gres 资源名问题**：本集群 `GresTypes = dcu, gpu`（`sinfo` 实测
`hx1hdnormal01 dcu:Hygon:8(S:0-7)`），原实现的 Gres/TRES 解析只认资源名 `gpu`，导致
任何海光作业都会被误判 `ALLOCATION_MISMATCH`。已扩展为同时接受 `gpu`/`dcu`。

**Slurm 字段格式问题**：该集群 `scontrol show job -o` 对这批作业（GUI 提交，
`JobName=STARCCM_PLUS_GUI_*`）**没有裸的 `Gres=`/`TRES=` 键**，只有
`AllocTRES=`/`ReqTRES=`（例如
`AllocTRES=cpu=128,mem=486G,node=1,billing=128,gres/dcu=8`）。原实现只认
`Gres`/`TRES` 两个键名，导致解析不到分配数量。已扩展为按
`TRES → AllocTRES → ReqTRES` 顺序回退查找。

**首次真机 `-gpgpu` run 结果**（8 卡，`--gpgpu auto:8:nomps`，资格文件人工核验
`sim_review.items` 依据是操作者本人在 STAR-CCM+ GUI 里对同一 `cifutest.sim`
的实际求解器/物理模型清单）：预检**全部通过**（`state: PREFLIGHT_PASSED`，厂商、
平台、8 张设备、占用检测、Slurm 分配、machinefile、sim hash 全部核验通过），
STAR-CCM+ 被正常拉起并注入 `-gpgpu auto:8:nomps -require-gpgpu-compatibility`，
但在建立并行会话阶段（`MachineHost::start`/`ServerSession::launchServer`，位于
`.../clang17.0-r8/lib/hip/cd/libStarMachine.so`）以 SIGABRT 崩溃（`star_return_code:
134`，`gpu_execution.json` 正确分类为 `state: FAILED`, `failure_code:
STAR_NONZERO_EXIT`，符合设计：预检通过 ≠ 求解成功）。

日志末尾提示：

```
Warning: Could not determine CPU architecture, please set -flexiblaslib <library>. Falling back to Intel MKL.
```

`starccm+ -help` 显示 `-mpi` 支持 `openmpi`/`openmpi40`/`openmpi41`/`intel`/`hpe`/
`crayex`/`fujitsu`，安装目录 `mpi/` 下确认打包了 `intel` 与 `openmpi` 两套。默认（不
显式指定）选中的组合在该海光节点崩溃；已给 `_build_starccm_command` 加
`-mpi <driver>` 支持（`--mpi-driver` CLI 参数，默认空、不改变既有 CPU 命令），
`-mpi openmpi` 是候选规避方案，**已验证不能解决问题**（见下）。

**追加验证（同日，`--mpi-driver openmpi` 实测无效）**：换成 `-mpi openmpi` 后
argv 确认已生效（`gpu_execution.json.command` 里有 `"-mpi", "openmpi"`），但
崩溃现象、退出码、日志内容**完全相同**，说明与 MPI driver 选型无关。日志开头
的 `-flexiblaslib`/Intel MKL 警告也是无关项（该机器上一直存在，与本次崩溃
无因果关系）。

**真正根因（完整日志确认）**：

```
[debug] set comgr isa with amdgcn-amd-amdhsa--gfx908:sramecc+:xnack-
LLVM ERROR: Missing device library for gfx908
[ROCT-Thunk-Interface/src/hymgr.c:435, WARNING]: Version mismatch
```

STAR-CCM+ 内置 comgr（`amdgpu/rocm_compiler_support/6.2.0-cda-001`）把这批海光
DCU 当作 AMD `gfx908`（MI100）编译目标，但：

- 本机系统级 DTK-25.04.4（`/opt/dtk-25.04.4`）的设备库只有
  `gfx906`/`gfx926`/`gfx928`/`gfx936`/`gfx938`，**没有 `gfx908`**。
- `rocminfo`（需要 `source`/设置 `LD_LIBRARY_PATH` 指向 DTK 才能跑，系统默认
  PATH 里没有）确认这张卡真实上报的架构是：

  ```
  Name:            gfx936
  Marketing Name:  BW
  Vendor Name:     C-3000
  → amdgcn-amd-amdhsa--gfx936:sramecc+:xnack-
  ```

即 **STAR-CCM+ 请求的 `gfx908` 和这张卡真实的 `gfx936` 完全是两个不同架构**，
不是"设备库缺失"，是 STAR-CCM+ 这个 build 内置的 GPU 编译支持组件对海光 DCU 的
架构探测/映射有误（或该组件版本 6.2.0 本身不认识这一代海光芯片，走了错误的
默认值）。这是 STAR-CCM+ 安装包本身的问题，不是本仓库预检代码或 CLI 参数能
解决的；已把 `--mpi-driver` 作为通用能力保留（对 CPU 路径无副作用），但它
**不是**本次崩溃的解法。

结论：B-03（设备查询）**全部解除**。B-01（`-gpgpu`/`-require-gpgpu-compatibility`
语法）**部分验证**——STAR-CCM+ 接受这两个参数并尝试启动 GPU 会话，未报参数错误，
但会话本身因架构探测错误崩溃，尚不能证明语法完全正确或 GPU 真的被使用。
B-05/B-06/B-07（数值/性能验收、GPU_CONFIRMED 证据）仍 BLOCKED：这次运行连
STAR 求解都没有真正开始，遑论确认 GPU 执行。下一步需要 STAR-CCM+ 供应商/超算
运维协助确认该 build 对海光 `gfx936` 架构的正确适配方式（更新/替换内置 GPU
编译支持包版本，或提供海光专门适配补丁），拿到 STAR 真正跑起来的日志后再评估。
