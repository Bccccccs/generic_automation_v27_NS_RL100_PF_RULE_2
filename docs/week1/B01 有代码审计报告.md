## 3. 10 分钟讲清楚：当前代码如何启动 STAR-CCM+

用户执行：

```bash
python run_case.py --config configs/config.yaml
```

执行过程：

1. 根目录 `run_case.py` 是兼容入口，调用 `generic_automation.cli.run_case.main()`。
2. `generic_automation/cli/run_case.py` 读取 CLI 参数。
3. `generic_automation/core/project_config.py` 读取 YAML/JSON 配置。
4. `parse_case()` 把配置转换成 `Case` 对象。
5. `resolve_case_dir()` 根据 `result_root + case_name` 得到输出目录。
6. `runtime_metadata.load_or_create_run_context()` 写入 `run_context.json`。
7. 如果 `ai_optimization.enabled=true` 且未加 `--no-monitor`，启动 `AIParameterGenerator` 作为内嵌 monitor。
8. `SimulationAdapter` 检查 backend，目前只支持 `starccm`。
9. `StarCCMAdapter` 根据 `case.run_mode` 选择输入 `.sim`：
   - `full_run` / `mesh_only`: 使用 `template_sim`
   - `solve_only` / `resume`: 使用 `input_sim`
10. `starccm_macro_builder.build_macro()` 读取 `starccm_macro_template.java`，生成本次运行的 `AutoSetupMacro.java`。
11. `StarCCMAdapter` 构造 STAR-CCM+ 命令：

```text
starccm_path -np num_cores -batch AutoSetupMacro.java input.sim
```

12. STAR-CCM+ 标准输出写入：

```text
<case_dir>/logs/starccm.log
```

13. Java 宏在 STAR-CCM+ 内部设置边界、网格、求解器、report、profiling 和 RL 文件握手。
14. 仿真结束后，`starccm_result_files.collect_reports()` 读取 report 和日志，写 `result.json`、`result_reports.csv`、profiling summary 等。

如果开启 monitor，则仿真过程中还会：

1. `AIParameterGenerator` 增量读取 `logs/starccm.log`。
2. `StarCCMLogReader` 解析 iteration table、残差、阻力、压力、CPU time。
3. `rl_observation_state.py` 构造 observation/state。
4. `rl_controller.py` 选择动作。
5. `rl_safety_override.py` 和 `rl_manual_rules.py` 做安全拦截和人工规则。
6. `ai_case_modifier.py` 写入 `rl/param_update.json` 和 `rl/pending_action.json`。
7. STAR Java 宏读取参数更新，应用后写 `rl/action_ack_events.jsonl` 和 `rl/param_update_ack.json`。

## 6. 当前 RL 控制变量

当前 RL 运行时变量由 `generic_automation/rl/rl_runtime_registry.py` 定义：

```python
RL_RUNTIME_PARAMETER_NAMES = (
    "pressure_relaxation_factor",
    "pressure_relaxation_initial_value",
    "pressure_relaxation_end_iteration",
    "pressure_amg_cycle",
    "velocity_amg_cycle",
)
```

含义：

- `pressure_relaxation_factor`: 压力松弛因子。
- `pressure_relaxation_initial_value`: 压力松弛 ramp 初始值。
- `pressure_relaxation_end_iteration`: 压力松弛 ramp 结束迭代。
- `pressure_amg_cycle`: 压力方程 AMG cycle。
- `velocity_amg_cycle`: 速度方程 AMG cycle。

这些都是数值求解器参数，不是喷气控制物理参数。

## 7. 为什么现有 RL 策略不能直接用于喷气控制

第一，动作空间不匹配。

当前动作是压力松弛上下调、ramp 调整、AMG cycle 切换。喷气控制需要的是喷口速度、质量流量、喷射角、喷口开关、占空比、频率、多喷口分配等动作。

第二，写回对象不匹配。

当前 `ai_case_modifier.py` 和 Java 宏写回 solver 参数。喷气控制需要写回 STAR-CCM+ 边界条件、profile、field function、mass flow inlet、momentum source 或 actuator 参数。

第三，观测状态不完整。

当前 observation 主要包括 residual、drag、total force、train surface pressure、CPU time 和 solver 参数。喷气控制还需要喷口状态、局部压力/速度/涡量、分离区指标、能耗、动量系数等。

第四，reward 目标不同。

当前 reward 偏向残差下降速度、CPU 效率、数值稳定性和 total force 偏离惩罚。喷气控制 reward 应该关注阻力降低、控制能耗、压力峰值、物理约束、动作平滑性和净收益。

所以现有 RL 不能直接用于喷气控制，但可以复用其在线监控、状态记录、动作写回、ack、profiling 和 offline replay 框架。
