# B02 喷气激励数据字典

这份文档解释 `runs/schedule_examples/` 下面每一种喷气激励结果里，每个文件和每一列数据代表什么。
这些数据是 STAR-CCM+ 的喷气边界条件输入表，不是 CFD 计算结果，也不是控制器输出的最优动作。

## 1. 总体目录

生成结果统一放在：

```text
runs/schedule_examples/
```

当前包含 6 类例子：

```text
no_jet_reference/   无喷气参考段
pulse_singlejet/    单喷气区脉冲
step_singlejet/     单喷气区阶跃
chirp_keyjets/      关键喷气区扫频
prbs_demo/          PRBS 伪随机开关
sparse24/           24 喷气区稀疏随机分组
```

每个目录里核心文件相同：

```text
actuation_schedule.csv       喷气动作主表，给 STAR-CCM+ 使用
config_summary.yaml          配置摘要、随机种子、统计量和校验结果
validation_report.json       机器可读的校验结果
actuation_heatmap.svg        喷气开关热图
total_mass_flow.csv          每个窗口的总质量流量
total_mass_flow_curve.svg    总质量流量随时间窗口变化曲线
```

## 2. actuation_schedule.csv

这是最重要的文件。每一行代表一个物理时间窗口。

统一列顺序为：

```text
time, window_id, t_start, t_end,
JET_01 ... JET_24,
cmd_massflow_01 ... cmd_massflow_24
```

### 2.1 时间列

| 列名 | 含义 | 单位 | 说明 |
|---|---|---:|---|
| `time` | 当前窗口对应的物理时间 | s | 等于 `t_start`，表示这一行动作从这个物理时间开始生效 |
| `window_id` | 喷气控制窗口编号 | 无 | 从 0 开始递增，0、1、2、3…… |
| `t_start` | 当前窗口开始时间 | s | STAR-CCM+ 应从这个物理时间开始使用本行动作 |
| `t_end` | 当前窗口结束时间 | s | STAR-CCM+ 应在这个物理时间结束本行动作 |

特别注意：这些时间是物理时间，单位是秒，不是 STAR-CCM+ 的内迭代步数。
一个物理时间窗口内部，求解器可能会做很多次非线性迭代，但那些迭代不出现在这个表里。

### 2.2 JET 开关列

列名为：

```text
JET_01, JET_02, ..., JET_24
```

含义：

| 数值 | 含义 |
|---:|---|
| `0` | 这个喷气区关闭 |
| `1` | 这个喷气区打开 |

例如：

```text
JET_03 = 1
```

表示第 3 个喷气区在这一物理时间窗口内打开。

```text
JET_03 = 0
```

表示第 3 个喷气区在这一物理时间窗口内关闭。

### 2.3 cmd_massflow 质量流量列

列名为：

```text
cmd_massflow_01, cmd_massflow_02, ..., cmd_massflow_24
```

含义：

| 列名 | 对应喷气区 | 含义 |
|---|---|---|
| `cmd_massflow_01` | `JET_01` | 第 1 个喷气区的指令质量流量 |
| `cmd_massflow_02` | `JET_02` | 第 2 个喷气区的指令质量流量 |
| `cmd_massflow_24` | `JET_24` | 第 24 个喷气区的指令质量流量 |

当前表里的质量流量是“指令值”。后续接 STAR-CCM+ 时，浩坤可以把它映射到对应喷口边界的 mass flow profile。

强制规则：

```text
如果 JET_05 = 0，则 cmd_massflow_05 必须等于 0
如果 JET_05 = 1，则 cmd_massflow_05 必须大于 0
```

这个规则对 24 个喷气区都一样。

### 2.4 一行数据怎么读

以 `pulse_singlejet/actuation_schedule.csv` 为例：

```text
time = 0.1
window_id = 1
t_start = 0.1
t_end = 0.2
JET_03 = 1
cmd_massflow_03 = 0.02
其他 JET = 0
其他 cmd_massflow = 0
```

意思是：

```text
在 0.10 到 0.20 秒这个物理时间窗口内，
只打开 JET_03，
JET_03 的指令质量流量是 0.02，
其他 23 个喷气区全部关闭。
```

## 3. 六种激励信号

### 3.1 no_jet_reference

目录：

```text
runs/schedule_examples/no_jet_reference/
```

作用：

```text
生成一段所有喷气区都关闭的基准数据。
```

数据特点：

```text
JET_01 ... JET_24 全部为 0
cmd_massflow_01 ... cmd_massflow_24 全部为 0
```

它用来回答的问题是：完全不喷气时，6 个载荷单元、总升力、阻力等基准水平是多少。
后面所有“有喷气”结果都可以和它比较。

### 3.2 pulse_singlejet

目录：

```text
runs/schedule_examples/pulse_singlejet/
```

作用：

```text
让单个喷气区短时间打开，然后关闭。
```

当前例子：

```text
JET_03 在 0.10-0.20 s 打开
其他时间关闭
```

它用来观察一个喷气区打开后，载荷响应是否有延迟、响应峰值在什么时候出现、
以及影响是否会传播到下游载荷单元。

### 3.3 step_singlejet

目录：

```text
runs/schedule_examples/step_singlejet/
```

作用：

```text
让单个喷气区打开后持续一段时间。
```

当前例子：

```text
JET_03 从 0.10 s 打开，持续到 0.80 s
```

它更适合观察持续喷气带来的平均变化，例如平均升力是否上升、阻力是否变化、
压力分布是否形成稳定偏移。

### 3.4 chirp_keyjets

目录：

```text
runs/schedule_examples/chirp_keyjets/
```

作用：

```text
让少数关键喷气区的质量流量按周期变化，并且变化频率逐渐升高。
```

当前例子使用：

```text
JET_03, JET_07, JET_14, JET_18
```

这些编号只是本周示例，最终喷气区编号需要和浩坤确认。

这个数据不是为了本周直接判断哪种频率最好，而是为了先让 STAR-CCM+ 能跑出一段
频率逐渐变化的输入响应。后续可以观察车底流场或载荷是否对某些频段更敏感。

### 3.5 prbs_demo

目录：

```text
runs/schedule_examples/prbs_demo/
```

作用：

```text
生成可重复的伪随机开关喷气输入。
```

数据特点：

```text
看起来像随机开关
同一个 random_seed 完全复现
换 random_seed 会生成不同序列
不超过最大同时开启数量
不超过最大总质量流量
```

当前配置限制：

```text
max_active_jets = 4
max_total_mass_flow = 0.08
```

它适合后续 ROM 或动态系统辨识。原因是 PRBS 比单次脉冲、单次阶跃包含更多输入组合，
模型能看到更丰富的动态响应。

### 3.6 sparse24

目录：

```text
runs/schedule_examples/sparse24/
```

作用：

```text
用较少窗口公平测试 24 个喷气区和少量三喷口组合。
```

当前约束：

```text
喷气区数量：24
每个激励窗口恰好开启 3 个喷气区
主激励窗口：72 个
无喷气参考窗口：8 个
总窗口数：80 个
每个喷气区在 72 个激励窗口中恰好出现 9 次
同一 3 喷气区组合不重复
同一喷气区不得连续开启超过 2 个窗口
random_seed 保存在 config_summary.yaml
```

它适合第一轮筛查：在不把所有组合都穷举一遍的情况下，尽量公平地让每个喷气区都有出现机会。

## 4. config_summary.yaml

这个文件记录生成表格时使用的关键配置和统计结果。

常见字段：

| 字段 | 含义 |
|---|---|
| `mode` | 激励类型，例如 `pulse_singlejet`、`prbs_demo` |
| `random_seed` | 随机种子，用于复现随机调度 |
| `n_jets` | 喷气区数量，当前为 24 |
| `total_windows` | 输出表共有多少个物理时间窗口 |
| `window_duration_seconds` | 每个窗口长度，单位秒 |
| `mass_flow_rate` | 默认打开时的单喷气区质量流量 |
| `max_active_jets_observed` | 实际生成结果里，一个窗口最多同时打开了几个喷气区 |
| `max_total_mass_flow_observed` | 实际生成结果里，一个窗口最大总质量流量 |
| `activation_counts` | 每个喷气区在整张表中打开了多少个窗口 |
| `validation.passed` | 表格是否通过自动校验 |
| `validation.errors` | 如果没通过，这里记录错误 |

`extra` 字段会随不同激励变化。例如 PRBS 会记录：

```text
random_seed
max_active_jets
prbs_switch_probability
```

chirp 会记录：

```text
jet_ids
chirp_start_frequency_hz
chirp_end_frequency_hz
```

## 5. validation_report.json

这是给程序读取的简短校验报告。

典型内容：

```json
{
  "passed": true,
  "errors": []
}
```

如果 `passed = true`，说明至少满足：

```text
表头是统一格式
window_id 连续递增
time 等于 t_start
t_end 大于 t_start
JET 列只包含 0 或 1
JET = 0 时 cmd_massflow = 0
JET = 1 时 cmd_massflow > 0
PRBS 等受限模式没有超过最大同时开启数量和总质量流量
```

## 6. total_mass_flow.csv

这个文件把 24 个喷气区的质量流量合并成每个窗口的总量。

列含义：

| 列名 | 含义 |
|---|---|
| `time` | 当前窗口起始物理时间，单位秒 |
| `window_id` | 时间窗口编号 |
| `t_start` | 当前窗口开始时间，单位秒 |
| `t_end` | 当前窗口结束时间，单位秒 |
| `active_jets` | 当前窗口打开了几个喷气区 |
| `total_mass_flow` | 当前窗口 24 个喷气区指令质量流量之和 |

例如 PRBS 中一行：

```text
active_jets = 4
total_mass_flow = 0.08
```

表示这一窗口同时打开了 4 个喷气区，每个喷气区质量流量为 0.02，总质量流量为 0.08。

## 7. 图文件

### 7.1 actuation_heatmap.svg

这是喷气开关热图。

读图方式：

```text
横轴：window_id
纵轴：JET_01 到 JET_24
蓝色：该喷气区在该窗口打开
浅色：该喷气区在该窗口关闭
```

它适合快速检查：

```text
无喷气参考段是否全空
pulse 是否只有一个短窗口打开
step 是否持续打开
PRBS 是否像随机开关
sparse24 是否比较均匀
```

### 7.2 total_mass_flow_curve.svg

这是总质量流量随窗口变化曲线。

读图方式：

```text
横轴：window_id
纵轴：total_mass_flow
```

它适合快速检查：

```text
无喷气参考段是否一直为 0
pulse 是否只有一个尖峰
step 是否有一段平台
chirp 是否有周期变化
PRBS 是否满足总质量流量上限
sparse24 每个主激励窗口总量是否一致
```

## 8. 和 STAR-CCM+ 的关系

这批文件现在还没有直接修改 STAR-CCM+ 边界条件。它们是给后续 STAR-CCM+ 接入使用的输入表。

后续接入时，每一行大致对应一个流程：

```text
读取 actuation_schedule.csv 的一行
  -> 根据 JET_xx 判断喷口开关
  -> 根据 cmd_massflow_xx 设置喷口质量流量 profile
  -> 让 STAR-CCM+ 推进到 t_end
  -> 读取载荷、阻力、压力等响应
  -> 写入真实 CFD 的 timeseries.csv
```

因此，本阶段最重要的是保证输入表格式统一、时间含义清楚、随机过程可复现、质量流量约束不被违反。
